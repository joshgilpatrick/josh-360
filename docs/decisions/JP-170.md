# JP-170 decisions

| Date | Ticket | Question | Option taken | How to undo |
| --- | --- | --- | --- | --- |
| 2026-11-19 | JP-170 | Which `session_lineage` kinds roll a session's cost into its parent? | Only `kind = 'subagent'`. A resume, fork or spawned session is a real session and keeps its own row. The roll-up walks `parent_uid` up through subagent edges only (not `root_uid`, which also climbs through resumes), so a nested subagent (S2 > S2a > S2b) lands on S2, and a subagent of a resumed session lands on the resumed session. | Change `session_subagent_roots` in the migration to also accept the other kinds. |
| 2026-11-19 | JP-170 | Which ticket does a subagent count toward when it and its parent are homed differently? | The ticket of its top session's row. A subagent is never a row of its own, even when it is homed to the ticket and its top session is not. | Not needed. |
| 2026-11-19 | JP-170 | A session that did a graph step on ticket A but is homed to ticket B: where does it appear? | Only under A, as a step row. "Not a graph step" rows are homed sessions that did no step in any run, so one session is never counted under two tickets. | Drop the "did a step in any run" filter in `ledger/ticket_costs.py`. |
| 2026-11-19 | JP-170 | One row per what, and what about a session that did two step attempts? | One row per step attempt that has a session, in start order. Gate and ask steps have no session and are not listed. When one session did several attempts, the first row carries its cost and later rows say "same session as <step> #<n>" with no cost, so the total counts it once. The total line counts distinct sessions (subagents folded in are not counted). | Not needed. |
| 2026-11-19 | JP-170 | How do `partly-priced` and `unpriced` show? | No cost rows or `unpriced`: "not priced yet". `partly-priced`: the cost, marked "(partly priced)". A row's status is the worst of its own and its subagents', so an unpriced subagent makes its parent partly priced. The total line says "N session(s) not priced yet" and, when any, ", M partly priced". | Not needed. |
| 2026-11-19 | JP-170 | `step_costs` cannot be redefined (migrations only add). How does the roll-up reach the view? | A new add-only migration `0002-step-costs-rolled-up.sql` adds the views `session_subagent_roots`, `session_costs_rolled_up` and `step_costs_rolled_up`; `step_costs` stays as it is. `measures.py spend`, `measures.py ticket` and the run report read the new view. `docs/design/data-model.md` is updated. | Revert the migration's readers to `step_costs`; the views can stay. |
| 2026-11-19 | JP-170 | Output format of `measures.py ticket`? | A text table by default, `--json` for the machine form. (`measures.py`'s other measures stay JSON-only.) | Not needed. |
| 2026-11-19 | JP-170 | What does the run report's cost column show for `--from-json` (a published snapshot has no cost)? | A dash for every row, with a note line under the table saying the snapshot carries no cost. | Not needed. |
| 2026-11-19 | JP-170 | The run report's step list is also what the runner publishes to the `laptop-status` branch, where cloud agents read it. May cost go in it? | No. `run_report` takes `with_cost`, which only the `report --run` command turns on; the published snapshot never asks for it, so it carries no cost (JP-112: working agents never see cost). A test checks the snapshot has no cost. | Pass `with_cost=True` in `snapshot`; not recommended. |
| 2026-11-19 | JP-170 | In the run report, a session that did several steps: does each row show the cost? | Yes, each step row shows its session's cost, because the report has no total to double count. Only `measures.py ticket` dedupes (first row carries the cost, later rows say "same session as"). | Not needed. |
