| Date | Ticket | Question | Option taken | How to undo |

| 2026-11-20 | JP-191 | Does Agent Manager have a kill command for the runner to call? | Yes. Agent Manager 0.47.1 (the laptop's version) has `agent-manager kill <session-id> [--json]`: it stops the agent's process, sets the row's status to `dead` and keeps the row, and `revive` brings it back on the same row. The binding calls it as `kill` in `binding.json`. | Change `kill` in `binding.json`. |
| 2026-11-20 | JP-191 | When does the runner kill a session whose result it has just recorded? | At once when Agent Manager shows it at rest, else `kill_grace_seconds` (1800) after the result was recorded, so a turn that is still finishing (hooks, a last message) is not cut off. It is filed in completed-steps at once either way. | Set `kill_grace_seconds` to 0. |
| 2026-11-20 | JP-191 | The ticket's "last session" needs its ticket Done, but the result is recorded before the `close` step moves the ticket. How is that decided? | Every finished session goes to completed-steps when its result is recorded. On the next pass after the ticket's newest run ends with the ticket in Done (the walker's `jira_status`, from `am-tickets.json`, never Jira), the newest session counts as the last one: it moves to `josh-360/tickets/Done` (archived `done_keep_days` after the run ended, as JP-173 does) and the `close-out` gate runs once. So the last session spends a few seconds in completed-steps. | Change `_last` in `amgroups.py`. |
| 2026-11-20 | JP-191 | "Every other state Done or Cancelled": what does the runner check? | That the newest session's step is finished and the ticket's newest run has ended with the ticket in Done. Earlier sessions are either finished (killed, in completed-steps) or abandoned (archived when the next attempt started), so none is still at work. | Add a check over the earlier sessions to `_last`. |
| 2026-11-20 | JP-191 | `close-ticket` and the validation graph already move tickets to Done. What does the new gate do (the Ready comment's flag)? | `close-out` does nothing to a ticket already in Done, never moves one in Deployed (its validation watch owns it, even one that gave up) or Cancelled, and moves any other status to Done with one fixed comment, through the same ticket port `close-ticket` uses. A ticket whose run ended in Deployed has no last session until its validation run ends in Done. | Change `LEAVE` in `graphs/gates/close-out.py`. |
| 2026-11-20 | JP-191 | Where does the gate run? | From the runner (`amgroups._close_outs`), through the walker's own `gates.run_gate` and `gates.jira_env`, outside the tickets file's lock. A failed gate is tried again on the next pass; `closed_out` is cleared when the ticket leaves Done, so a later Done closes it out again. No graph step names it, like `set-flag` and `post-comment`. | Remove `_close_outs` from `sync`. |
| 2026-11-20 | JP-191 | What if `finish` cannot take the tickets file's lock when the result is recorded? | The session file is written with `closes: true`, and the next sync takes the finish time from it. Sessions recorded before JP-191 have no `closes`, so they are never moved or killed (the ticket's "not in scope"). | Not needed. |
| 2026-11-20 | JP-191 | Does an earlier finished session still get archived when the next session starts (JP-173)? | No: it waits in completed-steps for its 7 days, killed. | 2026-11-20 | JP-191 | What does `graphs.completed-step-sessions` say when no finished session exists yet, and how long does it wait? | PASS ("none is left open"), because the validation watch reads `status is pass` and nothing finished means nothing is open; SKIP only when Agent Manager's database cannot be read.
