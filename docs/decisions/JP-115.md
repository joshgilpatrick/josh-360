# JP-115 decisions

| Date | Ticket | Question | Option taken | How to undo |
| --- | --- | --- | --- | --- |
| 2026-11-17 | JP-115 | What reviews the development graph's pull requests? | The laptop's PR audit (feature A21), the same one every josh-360 PR gets. The graph adds `review:needs-agent-audit` and waits for the verdict; it runs no code reviewer of its own. The ceremony's N rule (`docs/WORKFLOW.md` §4) decides another round. | Add a `code-reviewer` role step and the draft's record-audit gates. |
| 2026-11-17 | JP-115 | How does a graph wait hours or days for something outside it? | A new step kind `wait`, naming a gate script that answers `pending` until the event happens. No session is held, no loop is counted, nothing is changed. Additive, so the convention stays at version 1. Built by JP-115. | Model each wait as a role step whose binding does the waiting. |
| 2026-11-17 | JP-115 | Which tier does each development step use? | Designer mid; hardener gate, one revision round; builder cheap; build triager, plan reviewer and review fixer mid; PR writer cheap. Fixed by step, as Josh chose on 16 November. | Change a role's `tier`; the checker re-checks the loops. |
| 2026-11-17 | JP-115 | Does Josh approve the spec of a build ticket? | No (gap 1): the Opus hardener is the gate, and a designer's question goes back to triage. Josh approves the design of a Research ticket, since that is its deliverable. | Add an approval ask after `check_harden`. |
| 2026-11-17 | JP-115 | Who merges a development pull request? | The graph in josh-360 only (a new registry field `merges: agent`, default `josh`), with ready-for-human and green checks read fresh. Josh merges everywhere else, and the run waits for him without a session. | Set `merges` per system. |
| 2026-11-17 | JP-115 | Where do the development graph's working files live? | In the run folder, `$JOSH360_RUNS/<run>/work/`, from the first step, never in a worktree; the walker copies the spec, evidence and feedback to `saved/` at the end. This replaces the feature tree's note that the graph would use the durable output folder (S12). | Point `prepare-worktree` at another folder outside the worktree. |
| 2026-11-17 | JP-115 | How does an answer reach the session that asked? | The walker appends every answered ask, and every step output named `answer`, to `<run>/work/answers.md`; the designer, builder and fixer read it. | Pass answers through ticket comments. |
| 2026-11-17 | JP-115 | What happens when a pull request is closed without merging? | Clean up what is safe, move the ticket to Cancelled, end the run neutral. | Send the ticket back to triage instead. |
| 2026-11-17 | JP-115 | Who fixes checks that fail after the audit? | The same review fixer; the fix is a new code push, so it goes back to the audit (§4.4). | A separate checks fixer that keeps ready-for-human. |
| 2026-11-17 | JP-115 | What if the sprint skill or action-triage already holds the ticket? | `read_ticket` answers `not_here` and the ticket goes back to triage, so two runners never work one ticket. | Wait for the other runner instead. |
| 2026-11-17 | JP-115 | Where does the draft graph live before the `wait` step exists? | `docs/design/development-graph/development.yaml`, checked by `check_draft.py` (wait steps read as gates) and walked by `dry_walk.py`; the build moves it to `graphs/flows/development.yaml`. | Not needed once the build moves it. |
| 2026-11-17 | JP-115 | How should the builder work through a ticket's phases, given the run caps? | Josh chose one builder run per ticket (17 November, on the card in the JP-115 thread): one session builds every phase in order, one fresh helper per phase, and the scripts check every phase on the final tree. | Count the cap per phase (a convention change), or cap a spec at three phases. |
